# Контракт доставки для backend

Статус: действующий контракт. Telegram, VK, MAX и e-mail реализованы.

## Цель

После приёма заявки сайт создаёт одно нормализованное событие. Backend раскладывает его на независимые попытки доставки в активные каналы формы: Telegram, VK, MAX и e-mail. Один сбой не должен отменять доставку в остальные каналы.

## Единая модель данных

### Входящее событие формы

| Поле | Назначение | Источник |
| --- | --- | --- |
| `eventId` | неизменяемый UUID для дедупликации | клиент или backend |
| `projectId`, `formId` | владелец и форма | ключ интеграции |
| `submissionId`, `occurredAt` | трассировка заявки и время UTC | backend |
| `fields` | массив `{ key, label, value, valueType, isSensitive }` | форма сайта |
| `pageUrl`, `referrer`, `locale` | полезный контекст заявки | клиент, по согласию |
| `utm` | объект UTM-меток, если он нужен владельцу | клиент, по согласию |
| `requestId` | корреляция HTTP-запроса и логов | backend |

`ip` и `userAgent` не нужно по умолчанию пересылать в мессенджеры. Если они понадобятся для антифрода, хранить их отдельно с политикой минимального срока, а в сообщения включать только осознанно.

### Настроенное назначение

```ts
type Destination = {
  destinationId: string;
  formId: string;
  provider: 'telegram' | 'vk' | 'max' | 'email';
  label: string;
  status: 'pendingActivation' | 'active' | 'disabled' | 'invalid';
  configVersion: number;
  recipient: Record<string, string>;
  activation: 'notRequired' | 'awaitingRecipient' | 'verified';
};
```

Каналы принадлежат Relayform. Их токены, пароли и API-ключи живут только в защищённом серверном хранилище и вообще не являются частью tenant API. Клиент получает только адрес назначения, состояние подключения и инструкцию активации.

### Попытка доставки

Для каждой пары `eventId` + активный `destinationId` создаётся отдельная запись:

```ts
type DeliveryAttempt = {
  attemptId: string;
  eventId: string;
  destinationId: string;
  idempotencyKey: string;
  status: 'queued' | 'sending' | 'delivered' | 'retryableFailed' | 'failed' | 'cancelled';
  attemptNumber: number;
  providerMessageId?: string;
  providerStatusCode?: number;
  errorCode?: string;
  errorMessageRedacted?: string;
  createdAt: string;
  deliveredAt?: string;
};
```

## Получатель по каждому каналу

Пользователь не передаёт Relayform токен, пароль или логин провайдера. После выбора канала UI запускает подключение и сохраняет только подтверждённый адрес назначения.

| Канал | Что делает пользователь | Что сохраняем у назначения | Когда `active` |
| --- | --- | --- | --- |
| Telegram | нажимает «Подключить Telegram» и запускает бота по персональной deep link | внутренний `chatId`, полученный из `/start` | бот получил `/start` от этого пользователя |
| VK | открывает сообщество Relayform и отправляет выданную одноразовую команду | `vkUserId`, полученный из Callback API | секрет-проверенный `message_new` атомарно использовал действующий код |
| MAX | нажимает «Подключить MAX» и запускает бота по персональной ссылке | `userId` из webhook | защищённый `bot_started` атомарно использовал действующий токен |
| E-mail | вводит e-mail и подтверждает 15-минутной одноразовой ссылкой | нормализованный `email`, статус активации | токен из письма атомарно использован один раз |

### Telegram

Бот не может начать личный диалог первым: пользователь должен написать ему или открыть ссылку вида `https://t.me/<bot>?start=<signedState>`. В update `/start` Relayform получает `chatId` и связывает его с кабинетом. Пользователю не нужно знать или вводить этот ID. [Telegram: introduction to bots](https://core.telegram.org/bots)

В UI: одна кнопка «Открыть бота в Telegram» и статус «Ожидаем запуск бота» / «Подключено». Для группового чата — отдельный сценарий: пользователь добавляет бота в группу и даёт ему необходимые права.

### VK

Сообщения уходят от сообщества Relayform. Одного VK ID недостаточно: пользователь должен первым написать сообществу точную команду `/start <code>`. Backend хранит только digest 15-минутного кода, проверяет `group_id` и Callback API secret, затем атомарно сохраняет `object.message.from_id` как получателя. `random_id` на каждую отправку генерирует backend. [Официальная схема VK API](https://github.com/VKCOM/vk-api-schema)

В UI: ссылка «Открыть сообщество в VK», одноразовая команда и кнопка проверки статуса. Не просить token, VK ID или `peer_id` вручную.

### MAX

Для MVP поддерживаются личные сообщения по `user_id`; группы вынесены за рамки. Владелец открывает `https://max.ru/<bot>?start=<token>`, где одноразовый 32-символьный payload действует 15 минут, а база хранит только SHA-256 digest. Webhook принимает только событие `bot_started` с корректным `X-Max-Bot-Api-Secret` и атомарно сохраняет положительный `user.user_id`. Служебный токен Relayform передаётся только сервером в `Authorization`. Отправка использует фиксированный `platform-api2.max.ru`, а текст ограничен 4 000 символами. [MAX: POST /messages](https://dev.max.ru/docs-api/methods/POST/messages), [webhook subscription](https://dev.max.ru/docs-api/methods/POST/subscriptions)

В UI: «Открыть бота MAX», состояние ожидания и явная проверка статуса. Токен бота и сырой `user_id` не отображаются и не принимаются generic PATCH.

### E-mail

Пользователь вводит только адрес для уведомлений; Relayform отправляет письмо со своего подтверждённого домена и служебного транспорта. До активации адрес получает ссылку или код, иначе любой сможет направить чужие заявки на чужую почту. SPF/DKIM/DMARC и транспорт — внутренние настройки Relayform.

Владелец запускает отправку через защищённый `POST /v1/destinations/{destinationId}/email-activation`. Публичный `POST /v1/destination-email-activations/confirm` принимает непрозрачный токен; в базе хранится только SHA-256 digest. Ссылка действует 15 минут, используется один раз, а неизвестный, истёкший и использованный токены имеют разные безопасные результаты. Изменение подтверждённого адреса возвращает назначение в `pendingActivation`. До состояния `active` публичный event API отвечает так же, как для неизвестного назначения, и не создаёт доставку.

Уведомления отправляет Resend-адаптер с фиксированными темой, HTML/plain-text структурой и атрибуцией Relayform; пользовательский текст экранируется. Адаптер включается только при одновременном наличии `EMAIL_PROVIDER_API_KEY` и `EMAIL_FROM_ADDRESS`.

## Безопасность и валидация

- Проверять идентификатор получателя и состояние его активации на сервере. Токены и пароли принадлежат Relayform, шифруются в покое и не попадают в tenant API, логи, аналитику и трейс.
- Ограничить права служебных токенов, поддержать их замену и аудит. Изменение адресата, согласия и подтверждения должно попадать в аудит.
- Не позволять пользователю задавать произвольный URL доставки: адреса provider API определяет сервер. Это исключает SSRF.
- После сохранения выполнять безопасную проверку подключения. Проверка должна сообщать причину в редактированном виде и не отправлять тестовую заявку конечному получателю без отдельного действия пользователя.
- Шифровать интеграционные запросы только по HTTPS, валидировать входящий API-ключ/подпись формы, timestamp и защиту от replay. Конкретная схема подписи — отдельное backend-решение.
- Помечать чувствительные поля формы и применять отдельный срок хранения и маскирование для них.

## Надёжность и наблюдаемость

- Входящий `eventId` идемпотентен: повтор одного события не создаёт новую доставку для того же `destinationId` и `configVersion`.
- Доставка выполняется очередью. Повторять только временные ошибки (сеть, 429, 5xx) с экспоненциальной паузой, jitter, ограничением попыток и учётом `Retry-After`; постоянные ошибки (невалидный токен, неверный адресат, запрещённый template) переводить в `failed`.
- После исчерпания попыток сохранять запись для ручного повторного запуска. Кабинет показывает владельцу не более 20 последних ошибок только с form/provider/stable code/time. Project-scoped replay сбрасывает attempt budget, возвращает job в очередь и атомарно пишет requesting user, прежний safe code и число попыток в аудит; message и recipient не копируются в аудит или ответ.
- Метрики: принятые заявки, процент `delivered`, задержка доставки, число retry, ошибки по provider/коду и конфигурации. Логи связываются через `requestId`, `eventId`, `attemptId`, но содержимое формы маскируется.

## Разбиение первой backend-задачи

1. Схема `Form`, `Destination`, `Submission` и `DeliveryAttempt`; API CRUD назначения с recipient-only конфигурацией и состоянием активации.
2. Защищённый endpoint приёма заявки, валидация формы, создание нормализованного события и fan-out в очередь.
3. Контракт адаптера `validateConfig()` / `send()` / `normalizeError()` и один тестовый адаптер; статусы, идемпотентность и retry-очередь.
4. Экранные API: список форм, обезличенный статус канала, статистика доставок и redacted diagnostics.
5. Поочерёдные provider-адаптеры после подтверждения учётной модели и юридических условий каждого канала.

## Критерии приёмки

- Одна заявка с несколькими активными каналами создаёт независимые попытки; сбой одного канала виден в статистике и не блокирует остальные.
- API кабинета не принимает и не возвращает provider credentials; возвращает только recipient и статус активации.
- Повтор запроса с одним `eventId` не дублирует уведомление.
- Для каждого provider идентификатор получателя и согласие/первый контакт валидируются до активации; причина `invalid` не содержит секретных данных.
- Невозможно настроить произвольный URL назначения; все исходящие запросы идут только через выбранный adapter.

## Вопросы, требующие решения до реализации адаптеров

- Какие поля формы относятся к персональным данным, каков срок хранения и нужна ли региональная локализация?
- Нужен ли отдельный явный сценарий тестового сообщения для каждого канала? Ручной повтор финальной доставки уже реализован отдельно от тестовой отправки.
